# 零付费主流搜索引擎目录设计

## 背景

问舟的联网搜索是一个小型辅助功能，不应要求用户购买搜索 API、申请 API Key 或承担按次计费。当前实现已能使用 `requests` 直接请求 Bing 和 DuckDuckGo 公开结果页，但引擎目录不包含百度、Google、搜狗、360 搜索和神马等中国用户常用来源。

本设计将“直接 curl”理解为：使用项目已有的 `requests` 依赖向公开搜索结果页发送有界 HTTP 请求，而不是依赖外部 `curl` 可执行文件。这样可以保持 Windows、macOS 和 Linux 打包行为一致。

## 目标

- 不使用付费搜索 API、API Key、按次计费服务或项目托管的代理服务。
- 提供自动、百度、Bing、Google、搜狗、360 搜索、神马、DuckDuckGo 和自托管 SearXNG 的完整目录。
- 在 UI 中明确标注“直连”、“需要代理”和“自托管”。
- 保留现有超时、2 MiB 解压响应上限、禁止自动重定向、同源校验和结果 URL 过滤边界。
- 对验证页、明确无结果页和解析器失效做可观测区分。
- 保持已发布配置的网络路由语义，不把旧 SearXNG 请求静默切换成直连。

## 非目标

- 不在应用内提供代理地址、代理账号、代理密码、代理检测或代理订阅管理。
- 不负责选择 Google 的代理方案。用户自行通过 Clash Verge 等桌面系统代理或 TUN 保证网络可达性。
- 不绕过 CAPTCHA、JavaScript 验证页或其它访问控制。
- 不合并多引擎结果或重新计算跨引擎排名。
- 不在搜索功能 PR 中混入 CI gate 工作流、测试文档或分支保护配置。

## 引擎目录

| 引擎 ID | UI 标签 | 实现路径 | 是否进入自动模式 |
|---|---|---|---|
| `auto` | 自动（直连推荐） | Bing -> 百度 -> 360 搜索 | 不适用 |
| `baidu` | 百度（直连） | 固定公开 HTML 结果页 + 有界 HEAD 解链 | 是 |
| `bing` | Bing（直连） | 固定公开 HTML 结果页 | 是 |
| `google` | Google（需要代理） | 固定公开 HTML 结果页 | 否 |
| `sogou` | 搜狗（直连） | 固定移动 HTML 结果页 | 否 |
| `so360` | 360 搜索（直连） | 固定公开 HTML 结果页 | 是 |
| `shenma` | 神马（直连） | 固定公开 HTML 结果页 | 否 |
| `duckduckgo` | DuckDuckGo（需要代理） | 固定公开 HTML 结果页 | 否 |
| `searxng` | SearXNG（自托管） | 用户配置的 JSON 端点 | 否 |

“直连”和“需要代理”是面向中国大陆普通网络环境的可达性提示，不是持续可用性保证。标签只影响展示，不切换请求实现。

## 组件设计

### 引擎描述符

`ai_assistant.web_search` 保留一个权威引擎目录，每项至少包含稳定 ID 和 UI 标签。引擎 ID 用于配置持久化；UI 不根据名称反向推导行为。

`BUILTIN_ENGINES` 包含 `auto`、七个公开页面来源，不包含 `searxng`。内置引擎始终忽略并清空自定义端点；只有 `searxng` 需要用户端点。

### 共享请求层

所有结果页请求共享一个有界 fetch 实现：

- 搜索词规范化后长度为 1 至 500 字符；
- 结果数量为 1 至 10；
- 使用固定的浏览器兼容 `User-Agent`、`Accept` 和 `Accept-Language`；
- 使用现有连接/读取超时；
- `allow_redirects=False`；
- 响应有效 origin 必须与请求的固定或用户配置 origin 一致；
- 流式读取的解压响应正文不超过 2 MiB；
- 所有响应在成功和失败路径都关闭；
- 不传入应用级代理参数，桌面系统代理或 TUN 在应用之外生效。

每次 AI 请求线程仍使用自己的 `requests.Session`。搜索站点返回的 Cookie 可以在当次自动回退或百度解链中按域规则使用，但不持久化，并随请求线程销毁。

### 引擎解析器

每个解析器只负责一种响应格式，输出 `(title, url, snippet)` 行，最后统一经 `_normalize_results` 过滤。

- **百度**：解析真实 `c-container`/标题/摘要结构。对最终入选的最多 `limit` 个 `baidu.com/link?url=` 链接发送 HEAD，禁止跟随，只读取 3xx `Location`。返回目标必须是无凭据的 HTTP(S) URL。
- **Bing**：使用已有 `li.b_algo` 结构和 Bing 跟踪 URL 本地解码。
- **Google**：解析标准结果标题链接和摘要。对 `/httpservice/retry/enablejs`、验证码或已知人工验证标记先行报错，不伪装成空结果。
- **搜狗**：解析真实移动页 `vrResult`，从结果链接的 `url` 查询参数本地取得外部目标，不请求搜狗跳转端点。
- **360 搜索**：解析 `res-list`，优先读取链接的 `data-mdurl` 真实目标，不假定 360 跳转端点使用 302。
- **神马**：解析普通结果链接及 hydration JSON 中的 `dest_url`，两条路径都通过同一结果过滤器。
- **DuckDuckGo**：保留现有 HTML 解析、`uddg` 目标解码和 challenge 检测。
- **SearXNG**：保留现有 JSON 解析和端点校验。

## 数据流

### 显式引擎

1. 规范化搜索词、数量和引擎配置。
2. 只请求用户显式选择的来源，不回退到其它引擎。
3. 先检测验证页和明确无结果页，再解析正常结果。
4. 百度对入选结果做有界 HEAD 解链；其它 HTML 引擎不追加跳转请求。
5. 过滤并截取前 `limit` 个安全结果。

### 自动模式

`auto` 依次尝试 Bing、百度和 360 搜索。任一来源返回非空安全结果后立即停止，不请求剩余来源，不合并排名。

单个来源超时、连接失败、验证页、解析失败或无结果时继续下一来源。自动模式不尝试 Google、DuckDuckGo、搜狗、神马或 SearXNG，也不检测当前代理是否可用。

最坏请求上界为 3 次结果页请求，加上百度最多 10 次 HEAD 解链，共 13 次。不对同一来源做自动重试。

## 失败语义

- 验证码、Google `enablejs`、百度安全验证页和其它已知 challenge 抛出 `SearchHumanVerificationRequired`。
- 显式引擎的人工验证只终止当次搜索，不改写用户保存的搜索开关或引擎。
- 自动模式中只有 Bing、百度和 360 搜索全部返回人工验证时，才沿用现有保护行为关闭联网搜索。
- 明确的无结果页返回空列表。页面无结果节点且无无结果标记时，报告页面无法解析，不伪装成零结果。
- 百度单条解链超时、状态异常、缺少 `Location` 或目标不安全时，丢弃该条结果，不使整页失败。若最终没有安全结果，按该来源无可用结果处理。
- HTTP 状态、重定向、跨源响应、超时、连接和响应过大使用稳定中文错误。错误不包含响应正文、Cookie、内部异常、用户代理或可复用凭据。

## URL 安全

所有结果统一执行以下检查：

- 标题非空，最长 300 字符；
- 摘要最长 800 字符；
- URL scheme 只能是 `http` 或 `https`；
- URL 必须有主机，不得包含 username 或 password；
- 完整 URL 去重；
- 搜索站内跳转必须先用引擎专用、可测试的解码逻辑还原真实目标，不把 `javascript:`、带凭据 URL 或不透明跟踪地址传给模型。

## UI 与配置

搜索仍是默认关闭的显式 opt-in 能力。引擎下拉框按“引擎目录”的表格顺序展示。结果数量控件保持现有 1 至 10 的行为。

只有选择 `searxng` 时显示并启用自托管端点输入框。任何内置引擎都隐藏该输入框，并在验证/保存时将 endpoint 规范化为空字符串。UI 不增加代理控件或说明面板。

新建配置的 `search_engine` 为 `auto`。本轮尚未发布的 schema v3 保持版本号，扩展合法引擎 ID；已发布 schema v1/v2 仍可读。

### 迁移规则

- v2 `duckduckgo` 是直接公开页请求，保持 `duckduckgo`。
- v2 `bing`、`baidu`、`google` 和 `searxng` 都是用户 SearXNG 端点语义，统一迁移为 `searxng` 并保留规范化端点。这保留自托管网络路由，但新的单一 SearXNG 选项不保留旧 `engines=<id>` 精确过滤；这是已知迁移差异。
- v3 的 `auto`、七个公开页引擎和 `searxng` 按新目录验证并原样持久化。

迁移必须在常规配置验证前根据序列化版本执行，否则旧 `google` 会被错误解释为新直连 Google。

## 真实响应证据

2026-08-17 的无凭据冷请求仅作为当时、当出口的工程证据，不外推为持续可用性承诺。

| 来源 | 观测结果 | 解压正文大小 | 对设计的约束 |
|---|---|---:|---|
| 百度 | 200，9 个可用结果容器 | 1,307,857 | 保留 challenge 检测；安全 HEAD 解链 |
| Bing | 200，10 条结果 | 101,087 | 作为自动模式第一来源 |
| Google | 200，`enablejs` 中间页，零结果节点 | 91,761 | 必须区分人工验证与空结果 |
| 搜狗移动页 | 200，18 个 `vrResult` | 646,400 | 使用 `url` 参数本地解码 |
| 360 搜索 | 200，7 个 `res-list` | 548,957 | 优先 `data-mdurl`，不请求跳转端点 |
| 神马 | 200，11 个可用结果容器 | 412,074 | 支持直接链接和 hydration JSON |
| DuckDuckGo | 200，10 条结果 | 29,366 | 保留 challenge 检测 |

所有样本都低于现有 2 MiB 解压响应上限，因此不放宽上限。

## 测试设计

### 离线 fixture

从真实响应中提取最小结构片段，脱敏请求 ID、Cookie、个性化字段、跟踪参数和不必要内容，并在 fixture 注释中记录来源类型和脱敏方式。不提交 MiB 级完整搜索页。

百度、Bing、搜狗、360、神马和 DuckDuckGo 的正常结果 fixture 可从已保留响应提取。Google `enablejs` 失败 fixture 从已观测响应提取。Google 正常结果 fixture 必须来自真实可解析响应，或具有可追溯路径的开源解析器测试样本；在获得该证据前，不用手写 HTML 宣称 Google 正常解析已验证。

### 核心回归

`test/ai_assistant/test_ai_features.py` 覆盖：

- 每个 HTML 引擎的正常结果、明确无结果、验证页、异常结构和危险 URL；
- 百度 HEAD 使用 `allow_redirects=False`、最多 `limit` 次、有效 `Location`、恶意 scheme、凭据 URL 和部分解链失败；
- 搜狗 `url` 参数、360 `data-mdurl`、神马 `dest_url` 和 Bing/DuckDuckGo 跟踪链接的本地解码；
- 自动模式顺序、首个成功即停止、失败回退、不请求 Google/DuckDuckGo、全部验证和混合失败；
- 内置引擎忽略自定义 endpoint，SearXNG 保留现有验证与 JSON 解析；
- 共享请求层的超时、非 2xx、重定向、跨源响应、2 MiB 上限和响应关闭；
- 结果过滤器对非 HTTP(S)、缺少主机、带凭据 URL、空标题和重复结果的拒绝；
- v1/v2 迁移和 v3 新目录往返持久化。

`test/app/test_notice_search_ui.py` 覆盖：

- 九个引擎标签的文本、顺序和默认自动模式；
- 内置引擎隐藏 endpoint，SearXNG 显示、验证并持久化 endpoint；
- 引擎和结果数量持久化；
- 显式引擎验证失败不修改保存设置；
- 自动模式全来源验证仍触发联网搜索关闭；
- 旧 SearXNG 语义配置显示为自托管选项并保留端点。

实现按 TDD 顺序推进：先让新测试在当前实现上失败，再做最小实现，然后运行搜索核心测试、UI 测试和完整 `unittest` 发现。自动化测试不访问实时搜索站点。

## PR 隔离与提交格式

搜索专项 PR 只包含：

- `ai_assistant/web_search.py`；
- 必要的 `ai_assistant/config.py` 迁移；
- `app/AIInterface.py` 搜索控件；
- 搜索离线 fixture 和搜索/UI 回归测试；
- 本搜索专项设计文档和后续实施计划。

`.github/workflows/pr-tests.yml`、PR 模板、通用测试文档、Python 版本合约、`uv.lock` 和与搜索无关的测试修改属于独立 CI gate PR，不得混入搜索 PR。

`cooperate.md` 是本地双 Agent 协作记录，用于完成评审和 closing，但不进入上游产品 PR。

每个逻辑功能使用独立 commit。Commit 遵循仓库主流 Conventional Commit 格式：英文类型和可选 scope、ASCII 冒号、中文正文，例如 `feat(search): 增加主流搜索引擎目录`。

搜索和 CI gate 分别使用独立分支和 PR。在 fork、push 或创建任一 PR 前，单独向用户展示目标仓库、账号、分支、文件、完整 diff、精确标题和正文并取得确认。不自动合并，等待他人 review。

## 评审和验收

实现候选冻结后，Claude 通过 `cooperate.md` 接收结构化 handoff，并独立读取最新源码、完整搜索 diff、fixture 来源、测试日志和安全不变量。在所有 finding 终态、reviewer 给出终态 decision 且双方写入有效 closing ACK 之前，不宣称协作闭环。

搜索功能的验收条件为：

- 无付费搜索 API、API Key 或按次计费依赖；
- UI 完整展示九个选项和经批准的可达性标签；
- 七个公开页来源有独立适配器和失败语义，Google 不绑定 SearXNG；
- 应用不新增任何代理配置或凭据存储；
- 自动模式的顺序、停止条件和 13 次最坏请求上界有回归测试；
- 验证页、无结果和解析失败不被混淆；
- 重定向、同源、2 MiB 上限、URL 凭据过滤和响应关闭等现有安全不变量保持且有测试；
- 旧配置迁移不将 SearXNG 路由静默改为直连；
- 搜索与 CI gate 的分支、commit 和 PR 完全独立；
- 聚焦测试与完整测试结果如实登记，Claude 完成独立评审和双方 closing。

## 剩余风险

- 公开搜索页结构、反自动化策略和地区跳转会随时间、出口 IP 和站点发布变化；离线 fixture 只能保证对已知结构的行为。
- Google 在当前无代理出口下只返回 `enablejs` 中间页。在获得有来源的正常结果 fixture 和对应解析证据前，只能宣称验证页识别已验证，不能宣称 Google 正常结果解析已验证。
- 百度需要每条结果的 HEAD 解链，相比其它来源有更高请求数和时延。
- 搜狗移动页、神马 hydration JSON 和 360 `data-mdurl` 都是站点内部实现细节，可能在无通知的情况下变更。
- 旧 SearXNG 引擎特定过滤会迁移为通用 SearXNG 请求；端点和自托管网络路由保留，但结果集可能变宽。
